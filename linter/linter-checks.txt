The linter has two layers: a per-line **safety check** (`safety_check_line`) and the **structural/type parser** (`parse_line`). The safety layer now includes a path-sensitive **abstract interpreter** that tracks value ranges, initialization, pointer/heap state, string lengths and stack balance through branches, loops, switches and labels. Here is what it can detect.

## 1. Control-flow / structure

- Function not closed by `(funcend)` before the next function or at EOF
- `(funcend)` without an open function
- Unclosed `if` / `switch` / `for` / `do` blocks (inside a function or at EOF)
- `(else)` or `(endif)` without an open `if`
- `(switchend)` without an open `switch`
- `(break)` outside a `switch`
- `(next)` without an open `for`
- `while` without an open `do`
- Missing return value on at least one path in a function that declares return values (path-sensitive)
- No exit call (`(255 ... intr0)`) in the program
- Invalid exit call syntax, undefined/ non-integer exit variable
- Logical-flow bugs (dead branches, unreachable code, duplicate switch cases, missing return paths, ...) — see section 4.6

## 2. Function signatures / contracts

Using the annotation comments `// (func args ...)` and `// (return args ...)`:

- Wrong number of call arguments
- Argument type mismatch
- Return-value type mismatch
- Wrong number of return values
- Calling an undefined function when `// (func-strict)` is active
- Invalid type names in prototypes
- Strict mode (`// (func args S ...)`):
  - variables ending in `R` used as call arguments
  - variables consumed by a strict call being reused later
- `// (func args stpop)` mode: checks the order/types of variables popped with `stpop`
- `// (remove var)`: using a variable after it was marked invalid
- Function-call syntax errors (missing space/`(`/`:`, etc.)

## 3. Variables and types

- Invalid variable type in `(set ...)`
- Undefined variable used in a function call
- Duplicate variable declaration (treated as error)
- `(set ...)` without a variable name
- Pointer declared without uppercase `P` in strict pointer mode
- Pointer not `const-int64` in strict pointer mode

## 4. Safety checks (abstract interpretation)

The safety layer combines a fast interval analysis with an optional, more precise constraint solver pass. The interval analysis is described first; section 4.8 covers the solver.

### 4.1 Path-sensitive control flow

The safety layer follows the value and memory state through structured control flow:

- `if` / `else` / `endif`
- `for` / `next` and `do` / `while`
- `switch` / `case` / `break` / `switchend`
- labels and `jmp` / `jmpi`
- function boundaries

Comparisons in conditions refine integer ranges (`==`, `!=`, `<`, `<=`, `>`, `>=`). The false branch gets the negated condition, so guard patterns such as `(x zero ==) ... exit` are understood. At branch joins, definite initialization is the intersection of both paths, ranges are the union (hull), and "may" flags (may be null, may be freed, may be zero) are merged with OR. Code after an unconditional `return`, jump or exit is treated as unreachable until a jump label makes it reachable again. Loops are analysed with widening so induction and loop variables get body-wide bounds instead of only first-iteration values.

### 4.2 Integer safety

- **Uninitialized use**: reading a variable before it is definitely written on every reachable path
- **Integer overflow** in constant expressions, assignments, array indices, divisor expressions and range checks
- **Type narrowing**: source range does not fit the target `byte`, `word` or `doubleword`
- **Division / modulo** by:
  - a compile-time known zero
  - a range which contains zero
  - a value which may be zero on some path (for example after a branch merge)
- **`INT64_MIN / -1`** and **`INT64_MIN % -1`** overflow
- **Shift amounts** outside the range 0..63

Double division by zero is allowed.

### 4.3 Memory safety

- **Array indexing**: compile-time index, index interval, and actual byte offsets; detects negative, definitely out-of-bounds and may-be-out-of-bounds accesses
- **String indexing**: indexed access checked against the string capacity, including may-be-out-of-bounds
- **Heap indexing**: pointer offset and allocation size are tracked; detects heap access out of bounds and may-be-out-of-bounds
- **Pointers**:
  - pointer instruction with missing/undefined source or destination
  - destination not int64
  - destination not named `P<source>` in strict mode
  - pointer used before being set by a `pointer` instruction
  - pointer known to be `null` and then dereferenced
  - use after `dealloc` / `dealloc_vect` / `free_obj_memobj`
  - double free
  - invalid free of static arrays/objects
  - value used as array/pointer base without being an array and without a `pointer` instruction
  - strict mode requires a following `:check_pointer !`/`pointer_type` after a pointer is set
- **Heap leaks**: allocations still live at the final exit call are reported per variable
- **Array initializer count** greater than the declared array size
- **Compile-time ranges**: `(value min max range)`
  - minimum > maximum
  - value outside the range
  - works for int64 and double

### 4.4 Allocation and string buffers

- **Allocation size** known to be zero or negative
- **Allocation size overflow**: element count multiplied by element size exceeds `int64`
- Known allocation sizes are propagated to the following `stpop`, so later heap accesses can be bounds-checked
- **String buffer capacity** checks for:
  - `string_copy`
  - `string_cat`
  - `string_left` / `string_right`
  - `string_int64tostring` / `string_doubletostring`
  - `string_bytetohexstring` / `string_bytenumtostring`
  - `file_get_string` / `socket_read_string`
- Known string lengths are updated through copy, concatenation, substring and formatting calls. `string_len` and `string_search` results are modelled as ranges, so their results can be used in later bounds checks.

### 4.5 Stack safety

- **Stack underflow**: `stpop` needs more values than are known to be on the stack
- **Stack type mismatch**: `stpopi` / `stpopd` / `stpopb` and the popped variable type
- `stpush`, `stpushi`, `stpushd` and `stpushb` all contribute to the tracked stack depth
- Calls through `jsr` / `jsrind` and unknown library functions make the stack depth unknown instead of producing false positives

### 4.6 Logical bugs (CBMC-style)

The path-sensitive state is also used to report conditions which cannot behave as written:

- **Contradictory branch**: a constant comparison whose then or else branch can never be selected
- **Dead branch from ranges**: an interval proof that a branch is always taken or never taken (only with `// (logic-strict)`, see below)
- **Unreachable code**: statements after an unconditional `jmp`, `(return)` or program exit, until a jump label makes the code reachable again
  - compiler epilogue markers (`loadreg`, `break`, `(unsafe-end)` and the `intr0` tail ops 39/40/255) are not reported
  - code inside a branch already reported as dead, or inside a loop body, is not reported twice
- **Self-comparison tautology / contradiction**: `(x x ==)` is always true and `(x x !=)` is always false (floating point values are skipped because of NaN)
- **Duplicate switch case**: two cases of the same switch compare the same subject with the same value
- **Assignment to a constant**: writing to a `set const-...` variable
- **Self-assignment**: `(x x =)` which does nothing
- **Missing return path**: a function with a `// (return args ...)` contract can fall through to `(funcend)`
- **Assertions**: `// (assert (condition))` reports a condition which is always false at that point
- **Assumptions**: `// (assume (condition))` reports a condition which can never hold and therefore makes the following code dead

### 4.7 Interprocedural data-flow analysis

A pre-pass collects every function body and its `// (func args ...)` / `// (return args ...)` annotations. At each call of a known user function the callee is executed in a sandbox with the **actual argument value ranges** of the caller:

- **Argument-dependent findings**: a bug inside the callee that only happens for the concrete argument values (for example `division by zero` after the argument is divided) is reported at the call site, including the callee name and the source line inside the callee.
- **Return values**: the value ranges produced by `stpush` on the callee's `(return)` paths are merged and put on the caller's value stack, so a following `stpop` and the caller's own analysis can detect unsafe uses (for example a division by the returned value).
- **Effects on caller variables and globals**: the callee's final state of the caller variables is copied back by name, so writes and invalidations caused by unknown library calls inside the callee are applied. Arguments which the callee does not write keep their known values.
- **Nested calls**: calls inside the callee are analysed recursively. Diagnostics of a nested callee are forwarded once to the outer call site.
- **Recursion / limits**: recursive calls are not followed, the nesting depth is bounded and a global line budget stops very large analyses. Function-local declarations of the callee are removed from the sandbox first, so they cannot overwrite caller variables with the same name.

### 4.8 Optional constraint solver (bounded model checking)

When the linter is built with the Z3 development files available, an additional path-sensitive pass searches for mathematical contradictions that the interval analysis cannot express. `make.sh` enables it automatically (`-DHAVE_Z3`); without Z3 the linter is unchanged. The pass works like a small CBMC-style bounded model checker:

- **Split into parts**: every function is analysed separately.
- **Structured control flow**: the statements of a part are parsed into a tree of blocks, `if`/`else`, `for`/`next`, `do`/`while`, `switch`/`case`, returns and jumps.
- **Path constraints**: feasible paths are executed symbolically. Each integer expression becomes an exact 64 bit bit-vector; assignments, relations and assumptions are added to the path condition instead of being reduced to intervals.
- **Solver queries**: Z3 decides whether a branch is reachable, an assertion can fail, an assumption can hold, or a division/modulo/shift is unsafe on every feasible path.

Because it keeps relations such as `x + y == 10` and `x == y` instead of widening them to ranges, it can prove statements like "from `x + y == 10` and `x == 4` follows `y == 6`". It reports:

- **Assertions**: `// (assert (...))` which is always false on every feasible path leading to it
- **Assumptions**: `// (assume (...))` which can never hold, and therefore makes the rest of the path dead
- **Dead branches**: an `if` condition which is a tautology or a contradiction under the path constraints
- **Dead loops**: a `for` loop whose condition is already false before the first iteration
- **Division / modulo by zero** and **shift amounts outside 0..63** which are forced on every feasible path

Solver diagnostics start with `linter error: solver:`. A line already reported by the interval pass is not reported again.

The pass is deliberately conservative:

- Loops are unrolled up to a fixed bound; after that the affected variables become unknown and the path is marked imprecise.
- Calls of unknown functions, unsupported statements and exhausted query/path budgets mark the affected path imprecise.
- Diagnostics are only emitted from fully precise paths, so an incomplete model never causes a warning.
- Floating point variables, arrays and memory contents are not modelled by the solver; they fall back to the interval analysis.
- Function calls are not analysed interprocedurally by the solver; the caller state is over-approximated instead.

## 5. Opt-in controls

- `// lint-on` / `// lint-off`
- `// (func-strict)`
- `// (pointer strict on)` / `// (pointer strict off)`
- `// (func args stpop)`
- `// (func args S ...)` for strict function signatures
- `// (remove variable)`
- `// (logic-strict)` / `// (logic-lenient)`: trust or ignore branch reachability inferred from tracked value ranges (default: trust only compile-time constants and self-comparisons)
- `// (assert-strict)` / `// (assert-lenient)`: with strict, also report assertions which cannot be proven (default: only provably false assertions)

## Important limitations

The analysis is **compile-time**. Calls of known user functions are analysed interprocedurally with the argument ranges that are known at the call site; calls whose arguments are unknown, recursive calls and calls beyond the nesting or budget limit are treated conservatively. Only a small set of known library functions (allocations and string functions) is modelled. Values returned by unknown functions or loaded from unknown memory are treated conservatively.

The optional solver pass is bounded: loops are only unrolled a few times, it does not model arrays, memory contents or floating point values, and it does not follow function calls. Its diagnostics are therefore only a subset of the possible findings; when the model is incomplete it stays silent instead of guessing.

Ranges are intervals, not relational constraints: the linter may lose the correlation between two variables, so it can miss a bug or report that a value *may* be unsafe. At control-flow joins, ranges are widened to a hull and may-flags are unioned. For loops, widening gives bounds that cover all iterations, which is safe but imprecise. An unknown lower bound (`LLONG_MIN`) is not by itself treated as an out-of-bounds proof, to avoid false positives from imprecise joins.

A "may" warning means the linter cannot prove the access safe on every path; it does not necessarily mean the program is wrong. Bounds, null, overflow and range checks fire only when the required information is known or a definite/may-unsafe condition can be derived.

The final exit code is nonzero if any warning was emitted — warnings are reported as `linter error` and treated as errors (`l1vm-linter: N warning(s) treated as errors!`).
